# Mega Man X research: workflow, rules, status

The goal: **verified behaviour and readable C written from understanding**, checked against the real game frame by
frame — towards an accurate boss-fight demo (and maybe later a hand-written C port). Everything we claim is checked in
the game (Mesen 2, headless) by a `verify_*.py` suite, and every name lives in one checked set of records
(see the `sync-records` skill, which must be run after every completed run).

## Rules (from the project owner)

- **No static recompilation.** Never build a 65816→C translator, and don't base our C on MegaManXSNESRecomp. Borrow
  facts from other projects (names, code/data map) only after verifying them in the game.
- **Commit and push only when asked.**
- **Record names the moment they're confirmed** (functions, RAM, fields, X's steps too) and keep every record
  consistent (`sync-records`, `python3 check_records.py` → "records consistent").
- **Use screenshots when something doesn't make sense** (`Run.screenshot(frame, path)`, then look at the PNG).
- **Shared vs specific test code:** reusable tooling goes in `mesen_verify.py` (and older suites get retrofitted);
  logic that only makes sense for one boss stays in that boss's suite.
- A failing check caused by the test (wrong frame, stale value, bad input) is not a fact about the game: fix the test.
  A mislabelled or half-working editor value **is** a finding: fix it in `defs.py` and record it.

## Machine setup

1. **ROM**: `Mega Man X (USA) (Rev 1).sfc` (SHA-1 `C65216760BA99178100A10D98457CF11496C2097`) in the project folder or
   its parent (`params.STOCK_ROM` looks in both). Never commit it; `*.sfc` and `work/` are gitignored.
2. **Python 3.11+** with Pillow (the UI also needs tkinter). `python3 ui.py` creates `work/hack.sfc` from the stock ROM
   on first run; the suites need `work/hack.sfc`.
3. **Mesen 2** for the suites: `mesen_verify.MESEN` expects `../emulator/mesen.sh`, which sets `DOTNET_ROOT` (Mesen 2
   needs the .NET 8 runtime) and runs `../emulator/Mesen`:
   ```sh
   #!/bin/sh
   export DOTNET_ROOT="$HOME/.dotnet"
   exec "$(dirname "$0")/Mesen" "$@"
   ```
   Elsewhere, edit `MESEN` in `mesen_verify.py`. Runs use `Mesen --testrunner rom.sfc script.lua`.
4. **Save states** (`work/states/*.mss`) are regenerated by each suite's first step, except
   `storm_eagle_wing.mss`, which is made by hand (NOTES.md, "Getting to Storm Eagle"). `verify_player.py` uses
   `armored_armadillo_fight.mss`, so run `verify_armored_armadillo.py` first.
5. Check: `python3 check_records.py` (no emulator needed), then e.g. `python3 verify_armored_armadillo.py`.
   Optional reference: `~/Projects/external/MegaManXSNESRecomp` (clone of github.com/mstan/MegaManXSNESRecomp) for
   its `symbols/` export of the dizProjects disassembly — hints only.

On a Raspberry Pi 400 Mesen runs about 64 frames/s; `run_all` runs 4 sessions at once. **Run one suite at a time**:
two suites in parallel slow Mesen enough that long runs hit the timeout (`frames/8 + 180` s) and come back truncated.

## The Mesen runner (`mesen_verify.py`)

- `Run(level, x, y=None, frames, seed, infinite_hp, patch, savestate)`: builds a test ROM starting X at (x, y)
  (`testwarp.make_test_rom`; it centres the camera on X, so pick y to reproduce a checkpoint's camera), applies `patch(g)`
  to the ROM, and runs. `savestate=` starts from a saved state (loaded inside a memory callback).
- Logging: `track(obj_id, tag=)` (per-frame object fields, `TRACK_FIELDS`), `on_exec(addr, tag)` (A/X/Y/D at an
  instruction: log a random roll at the instruction **after** `JSL random`, where A holds it), `on_write(addr, tag)`,
  `each_frame(lua)`, `shot_log(tag, ids, lo, hi)`, `X_LOG`, `screenshot`, `save_state(when, path)`.
- Control: `input(lua)` returns buttons each frame (`right`, `left`, `b` jump, `y` shoot, `a` dash, ...);
  `at_exec(addr, lua)` runs Lua with `s` (CPU state) and `setreg(k, v)` at an instruction — force a value, a branch, a
  random column, a distance; `hold`, `poke`, `call(...)`.
- `fight_state(path, level, x, walk_input, when_lua, y=)` plays to the first fight frame once and saves a state.
- Analysis: `Fight(events, tag)` (`p`, `at[f]`, `starts`, `phase`, `after`, `calls`, `called`, `lives`, `timers`),
  `countdown(records, field, start)`, `report(results)`.
- Event frames: exec/hook events have `f = frame − 1`; per-frame records have `f = frame`. A phase's first record
  is the frame the step changed; the frame before a hook event is `at[c["f"]]`, the frame after is `at[c["f"] + 1]`.

## Workflow for a new subject (boss, X, room, engine routine)

1. **Read the code**: `decompile` the routine to a scratch file and read every handler; use `trace.listing` where the
   C is garbled (ternaries on joined paths, `damage_class = A`, distance compares). Note every constant, random roll,
   table, timer and call. Check `defs.py` params against the actual operands.
2. **Find the route**: checkpoints (`g.checkpoint(level, n)`), the boss event (`g.events(level)`, type 3, his id),
   doors (type 0 id 7), collision columns (`testwarp.collision_at`). Reproduce the checkpoint's camera (`y`).
3. **Explore** in a scratch script: walk in, track the boss, X and shots, take screenshots, print state changes.
4. **Write the suite** from the newest one as a template (`verify_sting_chameleon.py`, `verify_boomer_kuwanger.py`):
   fight-start state; natural runs at 3–4 X positions (one firing); runs with the attack table patched to one attack
   (`only(k)`); weapon runs (own a weapon: `w16(0x1F85 + 2*w, 0xDC00); w8(0x0BDB, 2*w)`); death (`SET_HP1`); X dying;
   value runs (patched params; values copied to RAM at init need `full=True`).
5. **Make chance exhaustive**: re-run a choice routine for every row and column **within one frame**: hook its final
   store, log the result, set `cpu.pc` back to its start with the next forced inputs. (An exec hook does not fire again
   for the instruction the PC is set back to, so advance the case counter in the loop hook.) Log every other random
   roll where it's read and check each outcome against its roll.
6. **Check**: every claim as a `check(name, ok, detail)`; details print the evidence that goes into VERIFIED.md.
7. **Run** (one suite at a time), fix test mistakes with `--cached`, rerun fully when a patch or input changed.
8. **sync-records**: defs/lift first, then VERIFIED.md (section + evidence), ENEMY_AI.md / PLAYER.md, NOTES.md (route),
   README, `RENAMED` for renames; `check_records.py` clean. Then report: confirmed, renamed, editor fixes, unchecked.

## Pitfalls already met

- The first frames after a state loads hold the old RAM (records at f ≤ 4 are junk); skip `f < 10`.
- **Busy frames**: some frames skip object updates; check durations with `countdown` on the timer, not frame counts.
  Values set "before the hit check" match the record of the frame before (damage class vs invulnerability timer).
- A step's first record often still carries the previous step's vx/values; a counter shared between attacks keeps a
  stale value on the attack's first frame.
- Phases cut by a hit, a guard, a counter, death (state 6) or the end of the run: exclude them, don't call them wrong.
- X dying restarts the stage: a new boss spawns with obj_start's damage class (3) and X respawns with full HP.
- Effects in the `$1928` list change their fields before the end-of-frame log; read sub-ids with `at_exec` where they're
  written. The effect list can be full, so "N pieces" may be fewer.
- The no-damage AR code (`7E0BD808`) blocks boss doors and makes X untouchable (no grabs, no Dead Lift, no drain):
  turn it on after the door, off when a test needs X caught.
- Setting a boss's beaten flag before his room makes entering it end the stage. To empty a room, clear the boss's
  object slot every frame instead (`verify_player.py`).
- Leftward speeds and repeated constants are often separate operands: check `mirror`/`copies` for every param by
  reading the code (Kuwanger's speeds, Armadillo's guard, Chameleon's lashes were half-working).
- Copy protection: SRAM checks and checksums of X's code change `$1F9E`, which can become X's jump gravity; patching
  X's code near `$81:8545`/`$81:853D` breaks his jumps.
- Exec hook at the target of a `setreg("cpu.pc", ...)` jump doesn't fire (see step 5).

## Status (2026-10-21)

- **All 8 main bosses verified**: Chill Penguin 44, Storm Eagle 35, Flame Mammoth 64, Spark Mandrill 41,
  Armored Armadillo 48, Launch Octopus 40, Boomer Kuwanger 30, Sting Chameleon 28 (committed 19a91c9).
- Game bugs found: Chameleon's high leap writes gravity into vy's low byte (vy $740); Armadillo stun-lock when his
  armor-break invulnerability is set below 90. Editor fixes: mirrors/copies above; renames `armor_invuln`,
  `whirlpool_jump`, `cloak_fade`, `stun_window`; one-attack tables that freeze Flame Mammoth are refused.
- **X in progress** (`verify_player.py`): walking ($178, step 2 for 5 frames), jump (vy $553, gravity 64; releasing
  resets vy), landing ($0A), wall slide (8 frames stuck, then −$200), wall jump ($178 away for 8 frames), dash
  (upgrades bit $08, $375 for 32 frames), dash jump, buster (≤ 3 shots, $440), charge (≥ 40 frames → projectile 1,
  ≥ ~110 → projectile 3), hurt (vx −$8A, vy $200, armor bit $04 halves vy, flash 60), fall cap (−$5C0 at full speed), damage and death —
  23/23, records synced (PLAYER.md). Charge exact: 31 frames → projectile 1, 101 → 3, 180 with the arm → 2 (+ $1D). Per-step speeds: table `$86:B9B1` (vx word, vy word, gravity byte per step × 3).

- **Boss rooms** (`rooms.py`, `verify_rooms.py`, 24/24): camera, borders, X/boss start, collision grid and a picture
